# ADR-009: Модель процессов плагинов

- Статус: ACCEPTED
- Дата: 2026-10-20
- Требования: PLG-012, PLG-022, PLG-040

## Контекст

Плагин — чужой нативный код: может упасть, зависнуть, аллоцировать
в audio thread. Нужно решить, где выполняются scan и обработка.

## Варианты

1. Всё in-process.
2. Scan out-of-process, обработка in-process.
3. Обработка в отдельном процессе на плагин (sandbox).

## Решение

Вариант 2, как в PLG-012.

- Scan: отдельный бинарник `jdance-plugin-scanner MODULE` загружает
  модуль, читает factory и печатает JSON с `PluginDescriptor`.
  Хост ждёт с таймаутом (по умолчанию 30 с); crash, таймаут или
  неверный вывод дают причину для blocklist (PLG-022).
- Загрузка и обработка: in-process. RT-половина (`Vst3Processor`)
  принадлежит audio thread, non-RT-половина (`Vst3Controller`) —
  UI thread (PLG-011). Общая часть (`Core`) уничтожается, когда
  исчезают обе половины, в обратном порядке lifecycle.
- Параметры UI → processor идут через SPSC-очередь и попадают
  в `inputParameterChanges` следующего блока с offset 0; выходные
  изменения — обратно через вторую очередь (PLG-042). Все буферы
  `ProcessData` выделяются при создании экземпляра (PLG-041).

Вариант 3 отложен до пост-MVP: встраивание GUI между процессами
(особенно macOS) и IPC в RT-пути.

## Последствия

- Падение плагина при обработке роняет приложение; защита — RT-030
  (panic strategy), autosave (PLG-075) и запрос при повторном открытии
  проекта (PLG-025).
- Хост не может гарантировать отсутствие аллокаций внутри плагина
  (PLG-040); тест RT-001 проверяет только код хоста.
